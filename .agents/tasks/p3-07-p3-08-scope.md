# P3-07 & P3-08 Scope Investigation

_Generated by read-only investigation step — no code was modified._

---

## Summary

**P3-07:** The invariant "never overwrite user-owned metadata during a rescan" is
already correctly modelled in `ScanMergeService` (inserts never touch
`isFavourite`, `watchProgressMs`, or `lastPlayedAt`), but there is one **latent
bug** at the DAO/repository layer: `insertVideoItem` calls `upsertItem` which uses
`insertOnConflictUpdate`. Because `title` and `updatedAt` are non-absent in the
companion, a UUID collision (theoretically impossible but worth guarding) or a
future call to `insertVideoItem` with an existing ID would silently overwrite the
title on the `VideoItems` row. The safer pattern is a pure `insertOrIgnore` (or a
conditional insert that only runs when the row is absent). Additionally, **`title`
on the `VideoItems` row is never updated after initial insert** — the service only
calls `updateSourceLocationMetadata` (which updates `displayName` on
`SourceLocations`, never `title` on `VideoItems`) — so a user-edited title is safe
in practice today. There are **no tests** that verify the full scan→merge→DB
pipeline end-to-end, and **no test covers `watchProgressMs` preservation**
specifically.

**P3-08:** No `test/integration/` directory exists. The unit-testable scope is
large (scan→merge pipeline, progress preservation under rescan, concurrent scan
safety). The device-only scope is limited to MediaStore permission flow on real
Android versions and SAF grant revocation detection.

## P3-07: What is already protected

### ScanMergeService (lib/domain/services/scan_merge_service.dart)

The class docstring (lines 18-28) states its invariants explicitly:

> "Never touches `isFavourite`, `watchProgressMs`, `lastPlayedAt`."

In practice, the code honour this:

- **New items** (lines 102-147): calls `repository.insertVideoItem(VideoItemInsert(...))`
  where `VideoItemInsert` (defined in `lib/domain/repositories/video_repository.dart`,
  lines 230-247) deliberately **omits** `isFavourite`, `watchProgressMs`, and
  `lastPlayedAt` as constructor parameters. Those fields cannot be passed in.

- **Existing items** (lines 84-100): calls `repository.updateSourceLocationMetadata(...)`
  — this only writes to the `SourceLocations` table (`displayName`, `availability`,
  `lastCheckedAt`). It never writes to `VideoItems`.

- **Missing items** (lines 150-167): calls `repository.updateSourceLocationAvailability(...)` —
  again, only the `SourceLocations.availability` column.

### AvailabilityCheckService (lib/domain/services/availability_check_service.dart)

The docstring (lines 30-40) states:

> "Never overwrites user-owned fields: `isFavourite`, `watchProgressMs`,
> `lastPlayedAt`, tags, or collections."

The implementation confirms this: the only write is
`repository.updateSourceLocationAvailability(location.id, newState, DateTime.now())`
(lines 99-107). No `VideoItems` fields are touched at all.

### LibraryRefreshService (lib/domain/services/library_refresh_service.dart)

This service is purely an orchestrator. It calls `adapter.listVideos(...)` and
`mergeService.mergeResults(...)`. It never calls any repository method directly
that would write to `VideoItems`.

### DriftVideoRepository.insertVideoItem (lib/data/repositories/drift_video_repository.dart, lines 171-198)

Calls `_dao.upsertItem(VideoItemsCompanion.insert(...))`. The companion is built
with only these present fields: `id`, `title`, `durationMs` (conditionally),
`widthPx` (conditionally), `heightPx` (conditionally), `createdAt`, `updatedAt`.
Fields `isFavourite`, `watchProgressMs`, and `lastPlayedAt` are **absent**
(`Value.absent()`).

The generated `toColumns(bool nullToAbsent)` in `app_database.g.dart` (lines
593-631) only includes a field in the SQL column list when `.present` is true.
Therefore Drift generates:

```sql
INSERT INTO video_items (id, title, [duration_ms, width_px, height_px,] created_at, updated_at)
VALUES (...)
ON CONFLICT(id) DO UPDATE SET
  title = excluded.title,
  [duration_ms = excluded.duration_ms, ...]
  updated_at = excluded.updated_at
```

This means `is_favourite`, `watch_progress_ms`, and `last_played_at` are **NOT in
the ON CONFLICT SET clause** and are therefore safe even if the row already exists.

## P3-07: Remaining gaps

### Gap 1 — `title` overwrite on conflict in `insertVideoItem` (latent bug)

`DriftVideoRepository.insertVideoItem` (`drift_video_repository.dart` lines 171-198)
calls `_dao.upsertItem(...)` which uses `insertOnConflictUpdate`. The `title` and
`updatedAt` fields **are present** in the companion. If `insertVideoItem` were ever
called with the ID of an existing row, it would silently overwrite the title. Today
this cannot happen in the normal scan flow because `ScanMergeService` only calls
`insertVideoItem` for URIs that were not found in the existing source-location
lookup — but the DAO has no guard preventing a second call from a different code
path. The safer pattern is `insertOrIgnore` (or `insert` with
`InsertMode.insertOrIgnore`) which skips the row entirely when it already exists.
There is no test covering this corner case.

### Gap 2 — `watchProgressMs` is never explicitly tested under rescan

No test in `scan_merge_service_test.dart` or `library_refresh_service_test.dart`
verifies that a non-zero `watchProgressMs` value survives a full rescan cycle
(set progress → refresh → read progress). The existing test (Gap 1 above) only
covers `isFavourite`.

### Gap 3 — `lastPlayedAt` is never explicitly tested under rescan

Same gap as Gap 2 but for `lastPlayedAt`.

### Gap 4 — Title survives re-scan only via `updateSourceLocationMetadata`, not end-to-end

There is a test (`scan_merge_service_test.dart:310`) verifying `title` is not
overwritten when `displayName` changes. However, there is no end-to-end test that:
1. Sets `title` to a user-edited value directly (simulating a future P5 title-edit feature),
2. Runs a full library refresh through `LibraryRefreshService`,
3. Confirms `title` on the `VideoItems` row is unchanged.

### Gap 5 — Tags and collections are not touched but are not tested under rescan

The docstring in `AvailabilityCheckService` mentions tags and collections are
preserved. However, no test in the domain layer verifies that tags/collection-items
are not deleted during `ScanMergeService.mergeResults` or
`LibraryRefreshService.refresh`.

### Gap 6 — No test for `insertVideoItem` called twice with the same ID

There is no test verifying that calling `insertVideoItem` twice with the same `id`
(same URI collision, which cannot normally happen but is a defensive contract test)
does not corrupt user fields.

### Gap 7 — `thumbnailCacheKey` does not exist yet

The field does not exist in the schema (no match in codebase search). Nothing to
protect. This is confirmed as out-of-scope for P3-07.

## P3-07: Recommended implementation

### 1. Fix `insertVideoItem` to use `insertOrIgnore` (file: `lib/data/database/daos/video_items_dao.dart`)

Change `upsertItem` to use `into(videoItems).insert(companion, mode: InsertMode.insertOrIgnore)`
instead of `insertOnConflictUpdate`. The docstring should say:
"Inserts a new video item row. If a row with the same `id` already exists, this
is a no-op — user-owned fields (title, isFavourite, watchProgressMs, lastPlayedAt)
are never overwritten." Name the method `insertItemOrIgnore` to make the semantic
explicit and avoid confusion with the old `upsertItem` name.

Update `DriftVideoRepository.insertVideoItem` to call the renamed method.

Rationale: The only safe update to `VideoItems` during a scan is done via the
targeted `saveProgress` / `setFavourite` / `updateTitle` (future) methods, not via
a bulk upsert. Defending the insert path with `insertOrIgnore` makes the invariant
enforce-by-construction.

Files to modify:
- `lib/data/database/daos/video_items_dao.dart`
- `lib/data/repositories/drift_video_repository.dart`

### 2. Add metadata-preservation tests (file: `test/unit/domain/scan_merge_service_test.dart`)

Add three new test cases to the existing `ScanMergeService (P3-04)` group:

- **`watchProgressMs is not overwritten by re-scan`**: Insert a VideoItem with
  `watchProgressMs = 45000`. Run `mergeResults` for the same URI. Assert
  `watchProgressMs` is still `45000`.
- **`lastPlayedAt is not overwritten by re-scan`**: Insert a VideoItem with
  `lastPlayedAt = <some epoch ms>`. Run `mergeResults` for the same URI. Assert
  `lastPlayedAt` is unchanged.
- **`insertVideoItem called twice with same id is a no-op for user fields`**: Insert
  a VideoItem with `isFavourite = true, watchProgressMs = 60000`. Call
  `repository.insertVideoItem(...)` again with the same `id` but different `title`.
  Assert both `isFavourite = true` and `watchProgressMs = 60000` and `title` is the
  original value (this test should initially FAIL against the current `upsertItem`
  code, confirming the bug, and should PASS after Fix #1 above).

### 3. Add a full pipeline test (file: `test/unit/domain/library_refresh_service_test.dart`)

Add one test: **`user metadata survives a full LibraryRefreshService cycle`**:
1. Insert a VideoItem with `isFavourite = true`, `watchProgressMs = 30000`.
2. Insert a SourceLocation for it.
3. Run `LibraryRefreshService.refresh` with a FakeVideoSourceAdapter returning
   that same URI.
4. Assert `isFavourite` and `watchProgressMs` are both unchanged.

This end-to-end test exercises the full stack: `LibraryRefreshService →
ScanMergeService → DriftVideoRepository → VideoItemsDao`.

### 4. Add a tags/collections preservation test (file: `test/unit/domain/scan_merge_service_test.dart`)

Add one test: **`tags and collection memberships survive a rescan`**:
1. Insert a VideoItem, a Tag, and a VideoTag linking them.
2. Run `mergeResults` for the same URI.
3. Assert the VideoTag row still exists.

## P3-08: Device-only scope

The following require the physical device **CPH2719 (Android 16, API 36)** or
another real Android device:

| Scenario | Why device is needed |
|---|---|
| `READ_MEDIA_VIDEO` permission request dialog appears correctly on API 33+ | `MethodChannel` can be faked in unit tests but the real system dialog requires Android |
| `READ_MEDIA_VISUAL_USER_SELECTED` partial grant handling on API 34+ | Requires the actual Android partial-grant flow |
| MediaStore query returns correct results after permission grant on a real library | Fake bridge cannot reproduce actual MediaStore row data |
| SAF folder grant survives app restart (persistable URI permission) | Requires real Android SAF and app-restart |
| SAF grant revocation detected correctly after simulated revocation | Requires Android to actually revoke the URI permission (cannot be faked reliably) |
| `LocalMediaAdapter` resolves a URI that exists on the real filesystem to `available` | Requires a real file on device storage |
| `LocalMediaAdapter` marks a URI `missing` after file deletion | Requires real file deletion on device |
| Large MediaStore library (1000+ items) scan completes without ANR | Requires real device / real MediaStore data |
| `LibraryRefreshService` does not run a full scan on every app tab change (LOCAL-008) | Requires running on device and switching tabs |

### Manual testing checklist for CPH2719

These steps cannot be automated and must be done manually after any code change:

1. **Fresh install**: Launch the app, trigger a MediaStore scan, grant
   `READ_MEDIA_VIDEO`. Confirm the library populates correctly.
2. **Permission denial**: Deny permission. Confirm the library shows empty/error
   state and no crash.
3. **Rescan with metadata**: Add a video to favourites (when P5-05 is available,
   or insert directly via DB for now). Trigger a manual refresh. Confirm the
   favourite flag is intact.
4. **SAF folder**: Pick a folder via SAF. Verify videos in the folder appear.
   Restart the app. Verify the folder is still accessible (persistable grant worked).
5. **SAF revocation**: Clear the originating app's data (or uninstall it) to
   revoke the SAF grant. Trigger availability check. Confirm items move to
   `permissionRevoked` and are not deleted.
6. **Missing file**: Delete a video file. Trigger a manual refresh. Confirm the
   item shows as `missing` and is not deleted from the library.
7. **Throttle**: Trigger an automatic refresh. Trigger it again within 15 minutes.
   Confirm the second one is suppressed.

## Key decisions for the implementing agent

1. **Use `InsertMode.insertOrIgnore`** (not `insertOnConflictUpdate`) in
   `VideoItemsDao.upsertItem`. Rename the method to `insertItemOrIgnore` to signal
   the no-op-on-conflict semantics. This is the minimal change that closes the
   latent title-overwrite bug without altering any existing public interface.

2. **Do not add a new `updateVideoItemTitle` repository method** in this task — that
   belongs to P5 (library edit). The current tests show the title is set correctly
   at insert time and never overwritten by a scan; that is the full requirement for P3-07.

3. **Do not create `test/integration/`** in this task. The device checklist above is
   documentation only; it will be acted on when the physical device is connected and
   a future task requires it.

4. **Update `TASKS.md`** for P3-07 and P3-08 only after all new tests pass and
   `flutter analyze` is clean.
